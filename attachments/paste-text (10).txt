# MATCHME — COMPLETE MOBILE & DESKTOP FEATURE PARITY
## One Unified Application Experience | Independent Responsive Layouts | Shared Functionality

### PRIORITY: HIGH — PLATFORM-WIDE IMPLEMENTATION

## 1. OBJECTIVE

Implement complete functional parity between the MatchMe mobile and desktop applications.

Every feature, action, workflow, and capability available to a Job Seeker on mobile must also be available on desktop.

Likewise, every relevant desktop feature must be available on mobile.

**CRITICAL: Do not change, duplicate, or overwrite the existing visual layouts of either platform.**

Mobile and desktop must maintain their own existing designs, navigation structures, spacing, component arrangements, and responsive behavior.

The goal is:

**100% functional parity with platform-specific visual experiences.**

This applies to all existing and future Job Seeker functionality.

Where appropriate, extend the same architectural principles to Company and Super Admin functionality without introducing unrequested interface redesigns.

---

# PART 1 — NON-NEGOTIABLE RULES

## 2. Preserve Existing Layouts

### Mobile

- Existing mobile-first design.
- Bottom navigation: Swipe | Dashboard | Profile.

- Mobile-specific popup and modal behavior.
- Swipe card layout.
- Touch interactions.
- Mobile spacing and typography.
- Safe-area handling.
- Existing mobile responsive breakpoints.

### Desktop

Preserve:

- Existing desktop navigation.
- Desktop sidebar or header structure.
- Existing desktop page layouts.
- Desktop spacing and typography.
- Existing desktop component arrangement.
- Desktop-specific interactions.
- Existing desktop responsive behavior.

Do not convert the desktop interface into a mobile-style layout.

Do not stretch mobile components across desktop screens.

Do not redesign the desktop navigation to match mobile navigation.

Do not replace the mobile layout with desktop-style tables or sidebars.

**Only add missing functionality within each platform's existing visual design.**

# PART 2 — SHARED FEATURE ARCHITECTURE

## 3. One Source of Truth

Both mobile and desktop must use the same canonical backend and business rules.

Reuse the existing:

- Supabase database.
- Authentication services.
- Job Seeker profile services.
- Company profile services.
- Vacancy services.
- Application services.
- AI Matching Engine.
- Preferences services.
- Credits system.
- Subscription and billing services.
- Resume services.
- Notification services.
- Messaging services.
- Settings and support services.

Do not create separate mobile and desktop databases.

Do not create independent mobile and desktop versions of the same business logic.

Do not duplicate API implementations unnecessarily.

Where mobile and desktop are separate clients, use shared service contracts, validation schemas, and reusable business logic.

### Architecture Principle

**Shared data + shared business rules + shared capabilities + independent UI presentation.**

# PART 4 — CROSS-PLATFORM SYNCHRONIZATION

## 16. Account Synchronization

A Job Seeker must be able to:

1. Log in on mobile.
2. Update their profile.
3. Open desktop.
4. See the updated profile.
5. Apply to a vacancy on desktop.
6. Return to mobile.
7. See the application and updated credit balance.

All changes must persist in Supabase.

Use account-based identity, not device-based records.

## 17. Real-Time or Refresh Synchronization

Use the existing supported synchronization architecture.

Where real-time subscriptions are already available, reuse them.

Otherwise, use reliable refetching or cache invalidation.

Ensure consistency after:

- Profile updates.
- Preferences updates.
- Applications.
- Saved jobs.
- Skipped jobs.
- Credit transactions.
- Subscription changes.
- Company status changes.
- Resume uploads.
- Messages.

Do not require users to log out and back in to see ordinary account updates.

## 18. Prevent Cross-Account Data Leakage

Verify:

- User A cannot see User B's private data.
- Switching accounts clears user-scoped cached information.
- Saved jobs and preferences remain user-specific.
- Credit balances are not shared between accounts.
- Application history is correctly isolated.
- RLS remains enabled and correctly enforced.

Do not weaken security policies to achieve synchronization.

- Breakpoints.

## 20. No Visual Regression

Before making changes:

- Inspect the existing mobile pages.
- Inspect the existing desktop pages.
- Identify existing functional differences.
- Record the current visual structure.
- Capture baseline screenshots where supported.

After implementation:

- Compare mobile layouts against the baseline.
- Compare desktop layouts against the baseline.

- Verify no missing controls.
- Verify no broken navigation.

Do not redesign a page merely because functionality is being synchronized.

# PART 6 — FEATURE PARITY AUDIT

## 21. Audit All Existing Features

Before coding, inspect the current implementation and build a complete feature parity matrix.

For each feature, identify:

- Available on Mobile.
- Available on Desktop.
- Uses Shared Backend.
- Functionality Matches.
- Data Synchronizes.
- Layout Preserved.
- Requires Fix.

Example:

| Feature | Mobile | Desktop | Sync | Action |
|---|---|---|---|---|
| Profile | Yes | Yes | Verify | Preserve layouts |
| VIA Resume | Yes | Verify | Verify | Add missing capability |
| Preferences | Yes | Verify | Verify | Synchronize |
| Saved Jobs | Yes | Verify | Verify | Ensure parity |
| Credits | Yes | Yes | Verify | Shared balance |
| Dashboard | Yes | Verify | Verify | Preserve layouts |

Use actual implementation findings, not assumptions.

Do not claim that a feature exists without inspecting its routes, components, and service integration.

## 22. Fix All Confirmed Parity Gaps

For each confirmed gap:

1. Identify the root cause.
2. Reuse existing shared functionality.
3. Add the missing capability to the affected platform.
4. Preserve that platform's visual layout.
5. Verify backend persistence.
6. Test the feature on both platforms.
7. Confirm no regression.

Do not rebuild working features.

Do not introduce placeholder functionality to satisfy the parity checklist.

# PART 8 — FUTURE DEVELOPMENT STANDARD

## 24. Permanent Feature Parity Rule

Establish the following project-wide engineering standard:

**Any new feature introduced on mobile must have equivalent functionality on desktop, and any new feature introduced on desktop must have equivalent functionality on mobile, unless an explicitly documented platform limitation applies.**

For every future feature:

- Use shared business logic.
- Use shared API contracts.
- Use the canonical backend.
- Preserve platform-specific UI.
- Include mobile and desktop acceptance tests.
- Verify synchronization.
- Check permissions.
- Prevent visual regressions.

Add this rule to the existing engineering standards and automated validation processes where supported.

Do not claim that a repository rule can control Atoms' internal agent behavior unless verified.
